Known gotchas for this migration

High NameID default differs

Entra commonly emits UPN while Okta defaults to email. Apps keyed on the old value create duplicate users or lock people out. Record the format per app.

High Conditional Access has no 1:1 export

Policies must be re-expressed as Okta authentication policies and Device Assurance rules. Inventory every policy and list what is dropped.

Medium Windows sign-in and join state

Entra-joined or hybrid-joined devices keep their join. Replacing Windows login with an Okta device-access product is a separate decision, so defer it from the first waves.

High App registrations used by automation

Graph API consumers, scripts, and CI pipelines use Entra app registrations that have no Okta equivalent and break silently.

High Passwords cannot be exported

Hashes do not move between IdPs. Plan delegated authentication against on-prem AD, a staged password reset, or passwordless enrollment before the cutover, and budget helpdesk volume for it.

Critical Two provisioners fighting over one app

If both IdPs push SCIM to the same app, one can deprovision accounts the other just created. Hand off one app at a time and import-match first.

High The old tenant does not disappear

Organizations on Microsoft 365 keep the Entra tenant as the Microsoft directory. The project replaces the primary authentication and app-access layer, and the scope must say so to avoid a false decommission date.

High Group nesting and dynamic rules do not port

Target group models may be flat. Nested membership that granted app access silently stops working after migration.

High New single point of failure

Everything now authenticates through one vendor. Keep break-glass admin paths that do not depend on the new IdP and document the outage runbook.

Medium Audit trail discontinuity

Sign-in logs live in two places during transition. Keep old logs for the retention period and route the new ones to the SIEM before first cutover; SOC 2 evidence spans both.

Info Verify vendor behavior

Feature gaps and limits change by release. Confirm each Critical and High item against current vendor documentation before committing dates.

Decisions to record (ADRs)

  • Provisioning source of truth: HRIS drives IdP / IdP drives apps from directory / Hybrid with explicit field ownership
  • Cutover model: App-by-app phased / Group-by-group phased / Big bang by domain
  • Device trust approach: MDM compliance signal / IdP-native device assurance / Defer to phase 2

Phases

1. Discover and decide
  • Build the integration inventory
  • Retire dead apps before migrating them
  • Decide MFA, device trust, and provisioning source-of-truth approach
  • Record decisions as ADRs
2. Build and mirror
  • Stand up target IdP, directory sync, and policies
  • Configure break-glass and logging to SIEM
  • Mirror group structure and test with IT pilot
3. Migrate in waves
  • Run waves in the order generated
  • Hold a go/no-go before each wave
  • Hypercare after every wave
4. Converge and retire
  • Remove old SSO trust and secrets per app
  • Close old provisioning connectors
  • Archive logs and update runbooks and audit evidence

Cutover day checklist

  • Go/no-go signed by wave owner and security
  • Pilot users confirmed working on the target before broad switch
  • App vendor contacted where IdP swap needs vendor action
  • Helpdesk briefed with a one-page FAQ and escalation path
  • Break-glass admin login verified outside the new IdP
  • Old IdP configuration exported and saved before any change
  • Monitoring on sign-in failure rate with an agreed rollback threshold

Rollback

  • Per app: restore previous IdP metadata and certificate (kept from the pre-change export)
  • Per app: re-enable old provisioning only after disabling the new connector
  • Domain federation: documented revert command and who may run it
  • Rollback trigger: sign-in failure rate or helpdesk ticket threshold agreed in advance

Exit criteria

  • Zero sign-ins to the old IdP for 30 days except break-glass
  • All provisioning owned by a single system
  • MFA enrollment at target percentage with recovery tested
  • Audit evidence reviewed by the security/compliance owner

Stakeholders

  • Security
  • IT / Helpdesk
  • App owners
  • HR (source of truth)
  • Compliance / audit
  • Executive sponsor

How to build the inventory

  • Entra: export Enterprise Applications and App Registrations (portal CSV or Graph) with SSO type, assigned users, and last sign-in
  • Entra: pull 90 days of sign-in logs by application to find real usage and dead apps
  • Entra: export all Conditional Access policies, named locations, and authentication methods policy
  • Okta: export Applications, Groups, Group Rules, Policies, and System Log activity by app
  • Ask app owners and Finance (SaaS spend list) for apps that never touched the IdP
  • Search code and CI for client secrets, tenant IDs, and issuer URLs
